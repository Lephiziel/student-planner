# Документация — Student Planner

Цифровая система планирования учебной деятельности студента: задачи с дедлайнами и приоритетами, учебные предметы, календарь, самооценка выполненных работ, статистика прогресса и браузерные напоминания о дедлайнах.

---

## 1. Общее описание

**Назначение.** Приложение помогает студенту структурировать учебные задачи, привязывать их к предметам, следить за дедлайнами через календарь и отслеживать собственный прогресс через дашборд и статистику.

**Тип приложения.** SPA (Single Page Application) на React + REST API на Go.

**Аудитория.** Один тип пользователя — студент. Каждый пользователь видит и редактирует только свои данные (задачи, предметы, оценки).

```

│   Browser (React SPA)        │
│   Vercel                      │
└────────────┬──────────────────┘

┌────────────▼──────────────────┐
│   Go / Gin API Server          │
│   Railway                       │
├─────────────────────────────────┤
│   Middleware: CORS, JWT Auth    │
├─────────────────────────────────┤
│   Handler → Service → Repository│

             │
┌────────────▼──────────────────┐
│   PostgreSQL                    │
│   Railway                       │
└─────────────────────────────────┘
```

### Слои backend

Каждый модуль (`user`, `auth`, `subject`, `task`, `grade`) построен по единой трёхслойной схеме:

- **Handler** — принимает HTTP-запрос, валидирует тело через теги `binding`, достаёт `userID` из контекста, вызывает Service, формирует HTTP-ответ.
- **Service** — бизнес-логика: проверки владения ресурсом, агрегация данных, обработка ошибок предметной области (`"task not found"`, `"email already taken"` и т.п.).
- **Repository** — единственный слой, обращающийся к БД через GORM.

Зависимости передаются через конструкторы (Dependency Injection), без глобального состояния — вся сборка происходит в `cmd/main.go`.

## 4. Модель данных

Все сущности используют `gorm.Model` (поля `ID`, `CreatedAt`, `UpdatedAt`, `DeletedAt` — мягкое удаление).

### User
| Поле | Тип | Описание |
|---|---|---|
| Email | string | уникальный |
| PasswordHash | string | bcrypt-хэш, не отдаётся в JSON |
| Name | string | имя пользователя |

### Subject (предмет)
| Поле | Тип | Описание |
|---|---|---|
| UserID | uint | владелец |
| Name | string | название |
| Color | string | hex-цвет для UI |

### Task (задача)
| Поле | Тип | Описание |
|---|---|---|
| UserID | uint | владелец |
| SubjectID | *uint | предмет (опционально) |
| Title | string | название |
| Description | string | описание |
| DueDate | *time.Time | дедлайн (опционально) |
| Priority | string | `low` / `medium` / `high` |
| Status | string | `todo` / `in_progress` / `done` |

### Grade (самооценка)
| Поле | Тип | Описание |
|---|---|---|
| TaskID | uint | привязка к задаче |
| UserID | uint | владелец |
| Score | float64 | оценка от 1 до 5 |
| Feedback | string | комментарий к работе |

### Связи

- `User 1—N Subject`
- `User 1—N Task`, `Subject 1—N Task` (опционально)
- `Task 1—N Grade`

Все выборки фильтруются по `user_id` — пользователь не имеет доступа к чужим записям ни на чтение, ни на запись (проверка реализована в Service и Repository через `WHERE id = ? AND user_id = ?`).

## 5. Функциональные модули

### 5.1 Авторизация
- Регистрация (email, имя, пароль ≥ 8 символов)
- Вход с выдачей пары токенов: access (15 минут) и refresh (7 дней)
- Эндпоинт обновления access-токена по refresh-токену
- JWT подписывается `HS256`, секрет берётся из `JWT_SECRET`
- Middleware проверяет заголовок `Authorization: Bearer <token>`, кладёт `userID` в контекст запроса

### 5.2 Предметы
- CRUD предметов с цветовой маркировкой (используется в UI: бейджи задач, события календаря)
- Эндпоинт статистики — количество задач и количество выполненных по каждому предмету

### 5.3 Задачи
- CRUD задач с приоритетом, статусом, дедлайном и привязкой к предмету
- Отдельный эндпоинт смены статуса (PATCH) — для быстрого изменения без полного обновления
- Фильтрация: по статусу, приоритету, предмету, диапазону дат дедлайна, текстовый поиск по названию (`ILIKE`)
- Эндпоинт сводной статистики: всего / выполнено / в работе / к выполнению / просрочено

### 5.4 Самооценка (Grades)
- К каждой задаче можно добавить одну самооценку (1–5) с комментарием
- При создании проверяется что задача принадлежит текущему пользователю
- Реализовано как инструмент рефлексии студента над собственной работой (без роли "преподаватель")

### 5.5 Календарь
- Отображение задач по датам дедлайна (FullCalendar, помесячный вид)
- Цвет события: цвет предмета — для активных, серый — для выполненных, красный — для просроченных
- Клик по событию открывает модальное окно с деталями задачи
- При переключении месяца подгружаются задачи нового диапазона дат через `due_from`/`due_to`

### 5.6 Дашборд
- Карточки со статистикой (всего/выполнено/в работе/просрочено) на основе `/tasks/stats`
- Прогресс-бар выполнения (% выполненных задач)
- Список последних активных задач
- Боковая панель с предметами

### 5.7 Браузерные уведомления
- При открытии приложения запрашивается разрешение `Notification API`
- Каждые 60 секунд проверяются задачи с дедлайном в ближайшие 24 часа
- По каждой задаче уведомление показывается один раз (ID хранится в `localStorage`)
- Работает только при открытой вкладке браузера (без Service Worker / фоновых push)

### 5.8 Тема оформления
- `ThemeContext` хранит выбранную тему (`dark`/`light`) в `localStorage` и применяет атрибут `data-theme` на `<html>`

## 6. Безопасность

- Пароли хранятся только как bcrypt-хэши, поле `PasswordHash` помечено `json:"-"`
- Все ресурсные эндпоинты (subjects/tasks/grades/users) защищены JWT-middleware
- Доступ к ресурсу проверяется на уровне репозитория: запись выбирается/изменяется/удаляется только если `user_id` совпадает с владельцем токена — иначе `404` (чтобы не подтверждать существование чужих записей)
- CORS настроен на конкретные origin'ы (локальный фронтенд + продакшен-домен на Vercel)
- На фронтенде access-токен автоматически обновляется через `refresh_token` при получении `401` (axios interceptor); если refresh не удался — пользователь разлогинивается

## 7. Запуск проекта

### 7.1 Предварительные требования
- Go 1.26+
- Node.js 18+
- Docker (для локальной PostgreSQL)

### 7.2 База данных

```bash
docker compose up -d
```

Поднимает PostgreSQL 16 (`planner_db`, пользователь `planner`, порт `5433`).

### 7.3 Backend

```bash
cd backend
cp .env.example .env   # заполнить значения, см. ниже
go mod download
go run ./cmd
```

Переменные `.env`:

| Переменная | Описание |
|---|---|
| `DB_HOST` | хост БД |
| `DB_PORT` | порт БД |
| `DB_USER` | пользователь БД |
| `DB_PASSWORD` | пароль БД |
| `DB_NAME` | имя БД |
| `JWT_SECRET` | секрет для подписи JWT |
| `APP_PORT` | порт backend-сервера (по умолчанию 8080) |

Backend доступен на `http://localhost:8080`, проверка живости — `GET /health`.

При старте выполняется `AutoMigrate` для всех моделей (`User`, `Subject`, `Task`, `Grade`) — таблицы создаются/обновляются автоматически.

### 7.4 Frontend

```bash
cd frontend
npm install
npm run dev
```

Frontend доступен на `http://localhost:5173`.

Переменная окружения `VITE_API_URL` задаёт адрес backend API (по умолчанию `http://localhost:8080/api`).

## 11. Известные ограничения и направления развития

- Уведомления работают только при открытой вкладке (нет Service Worker)
- Самооценка — это рефлексия студента, роли "преподаватель" в системе нет
- Нет email-верификации при регистрации
- Возможные доработки: повторяющиеся задачи, экспорт в CSV/Google Calendar, система рекомендаций по предметам, командная работа над задачами
